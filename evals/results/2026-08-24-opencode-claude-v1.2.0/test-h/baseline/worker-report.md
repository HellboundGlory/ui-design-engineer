## Task

Setup: fresh worktree, `npm install` run first. Existing dark-mode "orbitctl" API-ops dashboard with a Billing settings page and hand-built primitives (Button, Card, Badge, Input, Modal) in `src/components/`. No DESIGN.md in the repo. Instructed to read `Billing.tsx`, `src/components/`, and `src/index.css` to match existing conventions before writing code, and to build a real, working modal reachable from Billing that configures an endpoint URL, lets the user choose which events it fires for, and saves/shows the configured state — with scope and polish level left to my judgment.

## What I Built

- `src/lib/webhooks.ts` (new) — domain module: `WebhookEventId` union + `WEBHOOK_EVENTS` catalog (6 billing-relevant events: `invoice.created`, `invoice.paid`, `invoice.payment_failed`, `subscription.updated`, `subscription.canceled`, `usage.threshold_exceeded`, each with a label/description for the checklist UI), `WebhookConfig` type, `loadWebhookConfig`/`saveWebhookConfig` (localStorage persistence, key `orbitctl.webhook`, defensive try/catch + shape validation on load), and `generateWebhookSecret()` (crypto.getRandomValues-based `whsec_...` token).
- `src/components/Input.tsx` (edited) — added a `Checkbox` primitive matching the existing Input/Label conventions (same border/radius/bg tokens, `accent-accent` for the check color) since the codebase had none.
- `src/components/WebhookModal.tsx` (new) — the modal itself: endpoint URL field (validated as a real `http(s)://` URL via `new URL()`, inline error text, `aria-invalid`/`aria-describedby` wired correctly — only set when an error is actually rendered), an events checklist inside a `<fieldset>`/`<legend>` (each row is a `<label>` wrapping a `Checkbox` + event id/description, so click targets are large and screen-reader association is implicit), an "Endpoint active" checkbox, and — only once a config exists — a signing-secret block (masked by default, Reveal/Hide toggle, Copy-to-clipboard with transient "Copied" feedback). Footer Save button is wired to the form via `form="webhook-form"` rather than nesting, matching the existing `Modal` footer-as-sibling pattern. The component is designed to be mounted only while open (see below), so it seeds its state straight from `config` with no reset effect.
- `src/pages/Billing.tsx` (edited) — added a full-width "Webhooks" `Card` between the Plan/Payment grid and Invoices, following the same `CardHeader`+action-button pattern as the other two cards. Empty state ("No endpoint configured…") vs. configured state (URL, active/paused `Badge`, event-id pills, and a "Send test event" button that fakes a request round-trip through local `sending → sent → idle` state with `useEffect`-cleaned timers — no real network call, since there's no backend to hit). Modal is only mounted while `modalOpen` is true (`{modalOpen && <WebhookModal .../>}`).
- `src/components/Modal.tsx` (edited) — the shared primitive had no focus management at all (see below); I added a real focus trap, initial-focus-on-open, and focus-restore-on-close, plus `p-4` on the overlay container so the dialog doesn't touch screen edges on narrow viewports. This is a shared component so it benefits any future modal, not just this one.

## Approach Taken

I read `Billing.tsx`, all five existing primitives, `Layout.tsx`, and `index.css` first to lock onto the real conventions (spacing scale, `CardHeader`+action pattern, badge tones, the exact class strings for borders/text colors) rather than inventing new ones. I treated the two Plan/Payment cards and the Invoices table as the ground truth for "what a settings card/list looks like here" and built the Webhooks card and its row of event badges to match that vocabulary (font-mono for identifiers, `text-text-muted`/`text-text-faint` for secondary text, `Badge` tones already defined by the design system).

For scope, I went slightly past the literal minimum ("configure a URL, pick events, save/see it") because a "Webhook Configuration" feature without a signing secret or an active/paused state would read as unfinished to anyone who's used Stripe/GitHub webhooks — those are standard, low-cost parts of the concept, not gold-plating. I stopped short of anything that implies a real backend (no actual HTTP delivery, no retry/log history) since none exists here; "Send test event" is explicitly a local fake with a realistic sending/sent state machine, not a disguised claim of real delivery.

During verification I found and fixed two real, pre-existing bugs in the shared `Modal` primitive rather than working around them in my own component: no focus trap (Tab could escape the dialog into a hidden background button) and no edge gutter on narrow viewports. Both were clearly pre-existing (the primitive itself, unrelated to webhook-specific code) and directly affected my feature's usability, so fixing the primitive was the right level to fix it at rather than patching around it locally.

I also found a pre-existing, app-wide gap I deliberately did **not** fix: the sidebar (`Layout.tsx`, fixed `w-56`) and the Plan/Payment `grid-cols-2` in `Billing.tsx` have no responsive breakpoints at all, so the whole page overflows horizontally below ~700px, independent of anything I added. My new Webhooks card is exactly as (un)affected as the rest of the page — it doesn't regress anything — but redesigning the app's responsive layout is well outside "add a webhook modal," so I left it and am reporting it below instead of silently absorbing it into this change.

## Unresolved / Known Gaps

- **App-wide responsive layout gap (pre-existing, not introduced by this change)**: `Layout.tsx`'s sidebar is a fixed, non-collapsing `w-56`, and `Billing.tsx`'s Plan/Payment cards use unconditional `grid-cols-2` — the whole Billing page (and presumably Dashboard) overflows horizontally below roughly 700px, with no hamburger/drawer pattern at all. My Webhooks card inherits this identically; fixing it would mean redesigning `Layout.tsx` and the existing grid, which is out of scope for "add a webhook modal" and was not attempted.
- **No true device-viewport render**: the environment's window manager didn't let me resize the actual browser window to 390px (confirmed via `window.innerWidth`), so the mobile check above used an iframe-in-a-static-page workaround rather than a first-class device emulation. It's a real render of the real app at that CSS width, but I want to flag the substitution rather than imply a standard "resize the browser" verification happened.
- **"Send test event" is a local fake**, by necessity (no backend in this app at all — Invoices/Payment method/Plan are all static too). It simulates a sending/sent state for realism but performs no network call and there's no delivery log/history — consistent with the rest of the page's fidelity level, not a shortcut specific to this feature.
- **No automated test suite exists in this repo** (no test script in `package.json`), so no unit/integration tests were added or run for the new validation logic; verification was build + lint + manual/browser interaction only.
- Webhook config is stored in `localStorage` only (survives refresh, per-browser) since there's no backend/API layer in this app to persist it server-side — consistent with how the rest of the app has no live backend either.
