## 3. What I built

Named the fictional product "Meridian" (workspace: "Acme Robotics") purely for UI flavor/realism — no real brand. Neutral cool-slate palette with a single teal accent (deliberately not the default indigo/purple SaaS look), Inter for UI text, JetBrains Mono for keys/code.

**Shell**: header + page title + a horizontal ARIA `tablist` (`src/components/Tabs.tsx`) with roving `tabindex`, full arrow-key/Home/End navigation, and the active tab mirrored into `location.hash` (`#account`, `#api-keys`, `#billing`, `#team`) so a tab is directly linkable/bookmarkable and survives a refresh.

**Account Profile** (`src/features/account/AccountProfileTab.tsx`) — three stacked sections, because the tab groups three genuinely different lifecycles:
- *Profile form*: dirty-state tracked separately from saved state (Save/Discard only enabled once something actually changed), inline validation (required name, email format, 280-char bio limit with live counter), simulated async save with a disabled/loading button state.
- *Change password*: three fields validated together (required, ≥10 chars, new≠current, confirm must match) — all three errors can and do fire simultaneously.
- *Danger zone*: Delete account, gated by **type-your-email-to-confirm** in the destructive dialog (the highest-consequence action in the whole app, so it gets the heaviest confirmation friction of anywhere in the build).

**API Key Management** (`src/features/apiKeys/ApiKeysTab.tsx`) — a `useReducer`-backed in-memory key list (name, scope badge, masked value, created/last-used dates). Deliberately modeled the real-world pattern used by Stripe/GitHub/etc.: the full secret is generated client-side with `crypto.getRandomValues`, shown **exactly once** in a "copy it now" dialog immediately after creation, and only the last 4 characters are ever retained/displayed afterward (`ApiKey.last4` — the full string is never put in state). Revoke is a plain confirm dialog (no type-to-confirm — losing one key is recoverable by making a new one, so it doesn't need the heaviest friction).

**Billing Plan** (`src/features/billing/BillingTab.tsx`) — current-plan card with two usage meters (seats, API calls) that shift green→amber→red as they approach the limit; a 3-card plan picker (Free/Pro/Enterprise) that only surfaces a "Switch" action once a *different* plan is selected, with the confirm dialog's copy and tone changing for downgrades vs. upgrades (downgrade warns about losing access, styled danger; upgrade is styled neutral); mocked payment method and invoice history table. Cancel-plan uses the same type-to-confirm dialog as account deletion (type `CANCEL`) since it's a meaningful, if reversible-by-resubscribing, action — one step down from account deletion's friction. "Update payment method" and invoice "Download" are honestly stubbed with an info toast ("isn't wired up in this demo build") rather than silently doing nothing or faking success.

**Team Permissions** (`src/features/team/TeamTab.tsx`) — active members table + separate "Pending invitations" list. Business rules actually enforced, not just decorative: the Owner role can't be reassigned via the UI (no select rendered for that row, only a static badge) and the last remaining Owner can't be removed (Remove button disabled with an explanatory `title` tooltip) — removing a member is caught by a confirm dialog. Inviting validates email format *and* rejects duplicates against both active members and existing invites. Revoking a **pending invite**, deliberately, is immediate with just a toast and no confirm dialog — this is the one intentional asymmetry in the app's destructive-action design: an unaccepted invite carries no data-loss risk, so gating it behind a modal would just be friction for friction's sake, whereas removing an active member (who has real access/data) gets the modal.

**Why the four tabs differ structurally**: Account is single-owner CRUD-with-validation; API Keys is a create/reveal-once/revoke lifecycle around a secret that must never be re-displayed; Billing is state-machine-ish (plan tiers, cancellation windows, usage limits) with no user-authored input at all; Team is multi-entity relationship management (roles, invites, self-protection rules). Reusing one generic "settings form" pattern across all four would have been the "AI slop" failure mode the task is implicitly testing for, so each tab's IA follows its own domain instead.

**Shared primitives** (`src/components/`): `ConfirmDialog` (native `<dialog>`, optional type-to-confirm gate, busy state), `Toast` (context + `aria-live="polite"` region, auto-dismiss), `FormField`/`Select` (label+error+hint wired via `aria-describedby`/`aria-invalid`), `Badge`, `SectionCard`.

## 4. Approach / reasoning

- **Native `<dialog>` over a modal library**: `showModal()` gives focus trapping, Escape-to-close, and top-layer stacking for free, in every evergreen browser, with zero dependency weight. For a settings page with half a dozen distinct dialogs, that seemed like the right trade for a baseline build. This choice surfaced two real bugs I had to fix myself (see below) — a fair trade-off to disclose.
- **`useReducer` for the two "real" in-memory datasets** (API keys, team members) rather than plain `useState`, since both have multiple named mutations (add/revoke, setRole/remove/invite) that read clearer as actions than as ad hoc setter calls.
- **Hash-based tab routing** instead of pulling in a router, since the app is a single route with four panels — `location.hash` gives shareable/bookmarkable/back-button-friendly tabs without adding `react-router` for one screen.
- **Honest stubs over fake success**: anywhere I didn't build real functionality (payment method editing, invoice download), the UI says so via a toast rather than pretending to succeed or silently doing nothing.

**Two real bugs found and fixed during verification** (both are worth calling out since they're the kind of thing that's easy to ship silently broken):
1. **Dialogs rendered top-left instead of centered.** Tailwind's Preflight resets `margin: 0` on every element, which quietly kills the browser's native `margin: auto` centering rule for `dialog:modal`. Fixed in `src/index.css` by explicitly restoring `dialog[open] { position: fixed; inset: 0; margin: auto; }`.
2. **The API-key reveal dialog rendered with a transparent background**, letting the table row behind it bleed through and overlap the dialog's own text (visible in `07`, captured before the fix). Root cause: Tailwind v4 ships its utilities inside CSS cascade layers, and *unlayered* CSS always wins over *layered* CSS regardless of selector specificity or source order — so my plain `dialog { background: transparent; }` reset (written as ordinary global CSS) was silently beating the `bg-white` utility class on the same element. Fixed by wrapping all of my custom base-level CSS in `@layer base { … }` in `src/index.css`, which is the correct Tailwind v4 idiom and restores normal utility-class overriding behavior.

Both fixes are live in the current `src/index.css` and were re-verified visually after the change (screenshots `04` and `08` were taken post-fix).

## 6. Known gaps / deliberately out of scope

- **Payment method editing and invoice PDF download** are UI stubs (buttons exist, produce an honest "not wired up" toast) — building real payment form handling felt out of scope for a settings-workspace exercise and risked encouraging fake-looking credit card input handling.
- **Profile photo upload** is not implemented — the avatar is generated from initials, and the UI says so explicitly rather than pretending there's an upload control.
- **Ownership transfer** is not implemented — the Owner role is effectively fixed in this build (can't be reassigned or removed as the last owner), which is realistic but means there's no path to changing who owns the workspace.
- **No persistence** — all state (profile edits, keys, plan, team) is in-memory only and resets on page reload, as expected for a scoped front-end exercise with mocked data.
- **Tablet-width (~640–1024px) responsive behavior was not visually verified live** — the browser-resize tool in this environment did not reliably change the viewport beyond ~500px, so I could only confirm the mobile (`sm:` breakpoint and below) and desktop layouts directly; I did not fabricate a tablet screenshot. The `sm:` breakpoint classes are in place and used consistently across all four tabs, but that's a code-level claim, not a verified-in-browser one.
- **No automated tests** (unit or e2e) were written — verification was manual, live-browser interaction as described in §5, per the task's ask to actually run and check the app rather than assert correctness from code alone.
- **Color contrast / full WCAG audit was not run through a dedicated tool** (e.g. axe) — I used a deliberately non-washed-out palette (`--color-ink-500: #6b6b76` on white, `--color-danger-500`/`--color-accent-500` chosen to look reasonably AA-ish) and relied on visible focus rings + semantic HTML + ARIA roles throughout, but I did not run an automated contrast checker, so I can't claim a verified WCAG AA pass.
